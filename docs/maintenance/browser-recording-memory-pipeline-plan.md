# 浏览器录制内存管线优化方案

## 当前状态

- `Phase 1` 已完成第一版落地
- 当前实现位置：`src/webgal_agent/browser/screencast.py`
- 现在的录制热路径已经从“同步写盘”改为“base64 解码 + 有界内存队列 + ack”
- 后台 writer worker 负责异步写盘，录制结束后等待队列清空，再继续现有 FFmpeg 离线编码流程
- 若后台 writer 写盘失败或队列已满，录制会中止并抛出明确错误，避免无界内存增长

## 背景

当前录制链路位于 [screencast.py](/d:/GitRepository/WebGalAgent/src/webgal_agent/browser/screencast.py)，核心流程是：

1. `Page.startScreencast` 从 Chromium compositor 拉取 JPEG/PNG 帧
2. `on_frame()` 中将每帧同步写入 `data/browser/temp/...`
3. 录制结束后，调用 FFmpeg 离线编码为最终视频

这套方案的优点是结构简单、故障边界清晰，而且录制阶段不会被 FFmpeg 实时编码吞吐拖慢。当前主要瓶颈是 `on_frame()` 热路径上的同步磁盘写入。

## 当前问题

`on_frame()` 现在每帧都要做：

1. base64 解码
2. 同步 `write_bytes()` 落盘
3. 再发 `screencastFrameAck`

其中同步写盘最容易造成：

- 事件循环被阻塞
- `ack` 延后
- 后续帧接收节奏变差
- 实际录制帧率下降或掉帧

## 目标

优化录制热路径，尽量减少 `on_frame()` 中的阻塞操作，同时保持当前默认录制方案的稳定性和可回退性。

## 不建议直接切换到“全内存 + 实时 FFmpeg 编码”

设想中的方案是：

1. 帧不落盘，直接进入内存队列
2. 后台线程或子进程持续向 FFmpeg 管道写入数据
3. FFmpeg 在录制过程中实时编码

这个方向理论上可以减少磁盘 I/O，但不适合作为第一步默认实现，原因如下。

### 1. 瓶颈会从磁盘 I/O 变成实时编码吞吐

当前方案把编码压力完全推迟到录制结束后，因此即使 FFmpeg 很慢，也不会影响抓帧。

如果切到实时编码，只要后台消费速度跟不上前台收帧速度，就会出现：

- 内存队列积压
- 内存占用上涨
- 反压回到 `on_frame()`
- 最终仍然掉帧

### 2. 当前拿到的是压缩图像帧，不是原始像素帧

CDP screencast 返回的是 base64 包装后的 JPEG/PNG 图像，而不是原始 `rawvideo`。

这意味着如果要实时喂 FFmpeg，需要额外处理：

- 管道输入格式
- 帧边界
- 压缩图像流的持续写入稳定性

如果改为 Python 先解码成原始像素再喂 FFmpeg，又会增加 CPU 压力。

### 3. 音视频同步问题会更复杂

当前音频链路已经存在起止不同步风险。如果再加入实时编码线程和额外缓冲层，后续调试音视频同步会更复杂，因为需要额外追踪：

- 帧到达时间
- 入队时间
- FFmpeg 实际消费时间

## 推荐分阶段方案

### Phase 1：内存队列 + 后台磁盘写入

这是最推荐的第一步。

核心思路：

1. `on_frame()` 中只做最小工作：
   - base64 解码
   - 把帧数据放入内存队列
   - 尽快发送 `ack`
2. 后台 writer worker 专门从队列取帧并写入磁盘
3. 录制结束后仍然沿用现有 FFmpeg 离线编码流程

优点：

- 显著减轻 `on_frame()` 热路径负担
- 不改变最终编码逻辑
- 不引入实时编码吞吐风险
- 与当前调试、同步、回放方式兼容

需要补的设计点：

- 使用有界队列，避免无限占用内存
- 明确 writer 退出和收尾时机
- 录制结束时等待队列清空
- 如果 writer 失败，要能中止录制并给出明确错误

### Phase 2：实验性实时编码模式

在 Phase 1 跑稳之后，再考虑增加实验模式，而不是替换默认路径。

建议新增可选模式，例如：

- `capture_mode="disk"`：默认，保留当前离线编码路径
- `capture_mode="pipe"`：实验，走内存队列 + FFmpeg 实时编码

这样可以在不破坏默认行为的前提下，对比：

- 掉帧情况
- CPU 占用
- 内存占用
- 音视频同步表现
- 出错时的恢复能力

### Phase 3：评估是否值得提升为默认实现

只有在以下条件都满足时，才考虑把实时编码路径作为更正式的方案：

- 明确优于离线编码模式
- 不明显增加掉帧概率
- 内存和 CPU 占用可接受
- 音视频同步调试链路清晰
- FFmpeg 子进程生命周期管理稳定

## 实时编码模式的关键设计约束

如果后续要做 `capture_mode="pipe"`，建议按下面约束设计。

### 1. FFmpeg 应作为子进程，不是 Python 线程编码

真正做编码的是 FFmpeg，Python 线程只负责喂数据。重点应该放在：

- 队列设计
- 子进程管理
- 错误传播
- 退出收尾

### 2. 队列必须有界

必须提前定义队列满时的行为。常见策略有三种：

- 阻塞等待
- 丢弃新帧或旧帧
- 直接中止录制

这部分必须明确定义，否则系统行为会不可控。

### 3. 默认实现不应立即切换

实时编码更像“性能优化实验路径”，而不是简单替换磁盘写入。

当前默认实现的最大优点仍然是：

- 录制时不编码
- 错误边界清晰
- 易于定位掉帧原因

## 实施建议

推荐实施顺序如下：

1. 先实现 Phase 1：内存队列 + 后台磁盘写入
2. 为 Phase 1 增加调试指标：
   - 队列最大长度
   - writer 吞吐
   - 单帧平均写入耗时
3. 实测 Phase 1 是否明显改善掉帧
4. 再评估是否需要实现 `capture_mode="pipe"`
5. 若实现实时编码模式，必须以可选实验参数接入，不直接替换默认行为

## 当前结论

最值得优先做的不是“直接把帧放内存并实时编码输出”，而是：

**先把同步写盘移出 `on_frame()` 热路径，改成内存队列 + 后台磁盘写入。**

这一步风险最低、收益最高，而且不会破坏当前录制链路的稳定性和调试方式。
